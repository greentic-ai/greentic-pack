# Ship the `.gtxpack` inside the built `.gtpack`

Branch `BimaPangestu28/ship-gtxpack-in-pack`, off `origin/research` at
`8b4f95c` (`chore(release): 1.3.0-research.10`) — the version the designer's
`Dockerfile.tools` pins as `GREENTIC_PACK_BIN_VER`.

Closes step 4 of the table in §9.1 of
`greentic-designer/docs/superpowers/specs/2026-08-26-external-rag-integration-design.md`.

## The defect, reproduced

Before the change, a pack whose agent binds a `.gtxpack` tool built to exactly
this set of entries (captured from a deliberately-reverted tree, see
"Red-proof" below):

```
["manifest.cbor", "assets/pack.extensions.json", "assets/secret-requirements.json",
 "assets/setup.yaml", "pack.lock.cbor", "sbom.cbor"]
```

The *declaration* travels (`assets/pack.extensions.json`) and the *credential
form* travels (`assets/setup.yaml`, `assets/secret-requirements.json` — both
generated by opening the extension's own `describe.json`). The extension does
not. In a container the runner scans an empty `GREENTIC_EXTENSIONS_DIR/design/`,
drops the tool with a `warn`, and the operator's tool is silently gone after
they were asked for its API key.

## What changed, per file

### `crates/packc/src/cli/ext_resolver.rs`

- **`EXTENSION_ARCHIVE_PREFIX`** (`"extensions/"`) — the stable in-pack prefix.
- **`extension_archive_entry_name(&str) -> String`** — derives the ZIP entry
  name from an extension id.
  - Every character outside `[A-Za-z0-9._-]` becomes `_`. That removes both
    path separators, so an id can never address anything outside the archive.
    (Precedent: the designer's own `dep_for_extension`, which replaces
    `/ \ : whitespace` before using an id as a filename.)
  - Leading dots are stripped, so the entry can be neither a hidden file nor a
    bare `.` / `..` path component.
  - Sanitisation is lossy, so whenever it changed anything the name also carries
    the first eight hex digits of `sha256(<raw id>)`, joined by `~`.
    **Corrected after review — see "Review fixes" below: the digest suffix
    REDUCES collisions and does not eliminate them; the duplicate check in
    `package_gtpack` is the load-bearing guarantee.**
  - `sanitize_extension_id` is the private helper behind it.
- **`ResolvedExtensionArchive { extension_id, entry_name, bytes }`** — one
  acquired `.gtxpack`.
- **`AgentToolResolution { secret_requirements, archives }`** — the new return
  type of `resolve_agent_tool_requirements`, which previously returned the
  `BTreeMap` of secret requirements alone. The function already acquired the
  archive bytes in order to read `describe.json`; it now hands them back
  instead of dropping them. **This is deliberately one pass and one list**:
  declaring a dependency and shipping it must not become two sources of truth
  about which extensions a pack has, so the archives returned are literally the
  ones whose `describe.json` produced the requirements — not a second list
  re-derived from `pack.extensions.json`.
- The two in-file unit tests that asserted on the old bare-map return were
  updated to read `out.secret_requirements` / `out.archives`.
- New unit-test module `extension_archive_entry_name_tests` (5 tests) covering
  the verbatim case, traversal ids, the sanitise-alike case, an id that
  sanitises to nothing (`..`), and determinism.

### `crates/packc/src/build.rs`

- `use anyhow::{..., bail}` added.
- `BuildProducts` gains
  `extension_archives: Vec<ResolvedExtensionArchive>`, initialised empty at its
  six construction sites (one production, five test).
- The `!config.agents.is_empty()` arm now binds
  `let resolution = resolve_agent_tool_requirements(..)?`, keeps
  `resolution.secret_requirements` as the existing `tool_reqs`, and assigns
  `build.extension_archives = resolution.archives`.
- `package_gtpack` writes each archive under its entry name, sorted by entry
  name (deterministic ordering, matching the surrounding `dw_sidecars` /
  `extra_entries` handling), with SBOM media type `application/zip`.
  A duplicate entry name **bails** rather than being skipped — see below.

### `crates/packc/tests/extension_archive_in_pack.rs` (new)

Five integration tests, all of which shell out to the real `greentic-pack`
binary, build a real pack, and then **open the produced `.gtpack` and read its
entries**. Nothing is mocked; a test that asserted a function had been called
would prove nothing about the pack a customer receives.

1. `the_built_gtpack_carries_the_tool_extension_archive` — the entry
   `extensions/greentic.tavily.gtxpack` exists, is **byte-for-byte** the
   declared source `.gtxpack`, and is still a readable ZIP with its
   `describe.json` intact.
2. `the_credential_form_and_the_carried_archive_ship_together` — the pack asks
   for `tavily/api_key` *and* carries the tool. This is the invariant the whole
   change exists for.
3. `a_hostile_extension_id_stays_inside_the_archive` — an id of
   `../../../../etc/evil` produces exactly one archive, whose entry parses as
   exactly two ordinary path components (`extensions` + one non-dot file name).
4. `a_pack_with_no_extension_tools_carries_no_archive` — a worker with only a
   `flow:` tool gains no `extensions/` entry.
5. `an_unreadable_extension_dependency_fails_the_build` — see below.

## Fatal vs. loud warning: **fatal**, and it needed no new code

I chose fatal, and it follows what this repo already does rather than
introducing a new policy. `resolve_agent_tool_requirements` already documented
and enforced it:

> Errors (and propagates via `?`) when a declared tool extension is not found in
> `pack.extensions.json` or cannot be acquired — no silent skips.

Because the archive is carried out of that *same* acquisition — the one that had
to happen anyway to read `describe.json` — there is structurally no new failure
mode to decide about. An extension that cannot be read has already aborted the
build before any pack is written.

The reasoning for keeping it that way rather than downgrading: a warning here
would reproduce the exact defect being fixed, one layer up. A green build that
emits a pack whose setup form asks an operator for a tool's credential, and
which does not contain that tool, is precisely the silence §9.2 describes. The
build host is the last place that can still see both halves; past it, the only
signal left is a `warn` line in a runner log in a container. The cost of being
fatal is a failed build with a message naming the extension — recoverable in
seconds; the cost of a warning is a deploy that succeeds and a worker that
answers with fewer tools than the operator bound.

The one genuinely new failure I added is also fatal for the same reason: if two
archives would land on one entry name (only reachable via a truncated-digest
collision, since the ids themselves are unique `BTreeMap` keys), the build
`bail!`s naming the extension and the entry rather than letting the second
overwrite or be skipped. `written_paths.insert` returning `false` is silently
tolerated for `dw_sidecars`; for an extension it must not be.

`an_unreadable_extension_dependency_fails_the_build` pins all of this: the
build exits non-zero, the message names `greentic.tavily`, and no `.gtpack`
file is produced.

## What I deliberately did NOT build

No deploy-time unpack to `GREENTIC_EXTENSIONS_DIR`. §9.4 rejects it: it makes
the filesystem and the environment part of the deploy contract, so every target
needs its own unpack step and forgetting one fails silently — the mistake that
has already cost the MCP lane. The pack is the delivery vehicle, which is the
direction `component_source_from_packs` and `mcp_source_from_packs` already
took. The consuming half (the runner reading `extensions/` out of the pack) is
a separate change in a different repository and is not in this commit.

## Things I had to discover

- **`BuildProducts.dw_sidecars` was nearly the right vehicle but not quite** —
  it writes every entry with a hardcoded `application/json` SBOM media type and
  is documented as `dw-application`-only. A `.gtxpack` is a ZIP and extensions
  are not a dw-application concern, so it got its own typed field rather than
  overloading that one.
- **`extensions/` is already a *source*-tree convention**: the wizard writes
  `extensions/*.json` manifest sidecars into a pack directory, and
  `collect_extra_files` can walk them into the archive verbatim. They are
  `.json`, so they cannot collide with a `.gtxpack` entry — but this is exactly
  why the duplicate check bails instead of skipping.
- **`assets/pack.extensions.json` already ships in the pack** (visible in the
  pre-fix entry list above). So the *declaration* was already reaching the
  runtime; only the artifact it declares was missing. That makes the gap
  narrower and more clearly a bug than §9.1's table alone suggests.

# Review fixes (second pass)

Review returned "ready to merge, with fixes". Shipped behaviour was endorsed,
including the fatal-vs-warning call. Three fixes plus one contract ruling.

## 1. A doc comment that stated a constructibly false invariant

The original comment claimed *"a sanitised name can never equal an unsanitised
one"*, directly above the check that is the actual guarantee. It was false. The
verbatim branch accepts `-` and hex digits, so a legal id can carry exactly the
shape the lossy branch appended. The reviewer's counterexample:

- `sha256("a/b")[..8]` == `c14cddc0`
- `extension_archive_entry_name("a/b")` → lossy → `extensions/a_b-c14cddc0.gtxpack`
- `extension_archive_entry_name("a_b-c14cddc0")` → verbatim → **the same name**

The behaviour was already safe — `package_gtpack` bails and names both sides —
but the comment told the next reader that bail was redundant belt-and-braces
when it was the *sole* thing stopping one extension shadowing another. That is
this commit's own defect, one layer up: a comment that would stop someone
checking.

**Closed structurally as well as textually**, since it cost one character.
`LOSSY_MARKER` is now `~` instead of `-`. `~` is outside the verbatim branch's
`[A-Za-z0-9._-]`, so `sanitize_extension_id` maps it away and the verbatim
branch can never emit one. The two branches now occupy **disjoint namespaces**:

- `a/b` → `extensions/a_b~c14cddc0.gtxpack`
- `a_b-c14cddc0` → `extensions/a_b-c14cddc0.gtxpack`
- `a_b` → `extensions/a_b.gtxpack` (the common case is still readable — this is
  what keeps the contract shape `extensions/<id>.gtxpack` rather than forcing a
  digest onto every name)

The `ext-<hex>` empty-stem case became `ext~<hex>` for the same reason.

**What is still NOT closed, and is stated as such in both the code and here:**
two ids that sanitise alike *and* share their first eight digest hex digits. That
is a truncated-SHA-256 collision, and it fails the build loudly rather than
shadowing. So the duplicate check remains load-bearing, and both the function's
doc comment and the check's own comment now say so in those words.

New unit test `a_lossy_name_cannot_be_forged_by_a_verbatim_id` pins the
reviewer's exact counterexample, so a future change back to a shared separator
fails rather than silently reopening the overlap.

## 2. The duplicate bail had no test, and is reachable without a hash collision

file at `<pack>/extensions/<id>.gtxpack` in the source tree is carried as an
extra, and extras are written **before** the resolved archives. It claims the
entry first.

## 3. `Debug` on `ResolvedExtensionArchive`

`#[derive(Debug)]` over `bytes: Vec<u8>` meant one future
`tracing::debug!(?resolution)` would render a whole ZIP as a byte-array literal.
Replaced with a hand-written `impl Debug` printing `"<n> bytes"`.

Skipped per instruction: the sort clone, the partial `.gtpack` left on a
mid-write bail, and the wasm duplicated between `components/` and the archive.

## The cross-repo contract (coordinator's ruling)

Recorded as a doc comment at the write site in `build::package_gtpack`, stated
as a contract rather than an implementation note, because a `.gtpack` in a
customer's hands cannot be renamed later — the layout is fixed at the first
release that emits it.

1. A tool extension's `.gtxpack` travels at `extensions/<name>.gtxpack`, one
   flat level. **No kind partition** — not `extensions/design/`.
2. A consumer enumerates extensions by **filtering on the `.gtxpack` suffix**.
   It must not treat `extensions/` as homogeneous.
3. Rule 2 is load-bearing, not defensive: `extensions/` is *already* an
   authoring convention in a pack source tree — the wizard writes
   `extensions/*.json` manifest sidecars there and `collect_extra_files` walks
   them into the archive verbatim. Those `.json` files are not extensions and
   predate this feature.

Why flat, even though a runner's own on-disk model is kind-partitioned
(`<dir>/design/`): placing by kind would make packc read and trust
`describe.json`'s `kind` to decide a path. A design extension is today the only
kind ever declared as an agent-tool dependency, so that read buys a guess, not a
guarantee — and a wrong guess is baked into shipped bytes. The consumer already
opens each archive and can classify from the inside, where the answer is
authoritative.
